# Roadmap

The single list of planned and in-progress work for `dsc`. Checked entries may be implemented on `main` but not yet released; released history lives in [CHANGELOG.md](../CHANGELOG.md). Unreleased completed work is described as "implemented on `main`", not "shipped".

Legend: [x] done, [~] in progress or partially done, [ ] not started. Stable roadmap codes (`R1`, `R2`, …) are never renumbered or reused.

**Product boundary, 2026-09-21:** `dsc` is a local-first operations and state-management tool for people responsible for multiple Discourse installations. New work should deepen fleet selection and aggregation, reviewable file persistence, scripting, compliance exports, guarded mutations, or SSH/Docker/storage operations. Do not add a command solely to let an AI search, read, or participate in one forum when [Discourse's built-in MCP server](https://meta.discourse.org/t/connect-your-ai-apps-to-your-community-with-discourse-s-built-in-mcp-server/412755) already covers it. An overlapping CLI surface still earns its place when it provides deterministic export, local files, dry-run/diff, unattended automation, stronger verification, or cross-forum behavior. Existing commands remain supported.

## Planned

### Ops reliability

- [~] **R42 - `dsc update` failure detection and disk-guard recovery** - implemented: disk recovery, bounded SSH diagnostics, reboot verification by changed/stable Linux boot ID, mandatory final Discourse version retrieval, unchanged-commit detection after a requested rebuild, sequential stop-on-first-failure, and parallel stop-admitting-on-failure. Recurrence captured on 2026-09-23 with `dsc 0.19.0 update all -y`: reboot SSH disconnects were silently skipping readiness, causing immediate launcher exit 255 (`Connection reset by peer`/`Connection refused`). Remaining reliability phase: durable detached rebuild operation IDs/status/logs for safe observation across local Ctrl-C or a mid-rebuild transport loss; raw launcher exit 255 remains non-retryable until that exists. Spec: [update-failure-detection](commands/update-failure-detection.md).
- [ ] **R54 - Agent-facing mutation controls** - adopt the useful safety patterns confirmed in Discourse's built-in MCP server and official `@discourse/mcp` package without duplicating either tool surface: a shared adaptive per-forum write governor that pauses all work for a host after a 429 and lowers concurrency; explicit command-family allowlists for a future `dsc job` rather than arbitrary shell or API execution; fresh-state preconditions and exact post-write verification for high-impact mutations where feasible; bounded, redacted diagnostics that distinguish an unavailable plugin/capability from a missing resource. Driver: agents and fleet jobs can amplify request bursts and mutation mistakes; Discourse's opt-in capability exposure, user-scoped authorization, confirmations, bounded output, rate limits, and capability-specific errors demonstrate practical safeguards. Out of scope: an MCP server, dynamic remote-tool discovery, or HTTP transport in `dsc`.

Remaining: Phase 3's bulk file-driven mode - demand-driven; no live driver has asked for it since Phase 2 shipped. Others to survey: saved Data Explorer queries (`created_by`), uploads (`user_id`), personal-message participants, badges, reviewable claims. ### New command surfaces

- [x] **R62 - `dsc open` fleet selection and name globs** - implemented on `main`: `--all`, `--tags <tags>` through the shared `selected_discourses` selector, and `*`/`?` glob patterns in the name argument. Fleet selections launch every opener detached so one slow opener cannot serialize the rest, while a single exact name keeps `dsc open`'s checked-exit, interactive-stdio contract. Driver: a user wanting to open all configured forums in tabs in one command (2026-09-16).

- [x] **R53 - `dsc file audit|push|pull`** - complete (all phases implemented on `main`, v0.17.0/v0.18.0): checksum-verified regular-file transfer over configured SSH hosts. `file audit` compares local vs remote SHA-256/size per forum without transferring contents; `file push` stages via same-directory `mktemp`, verifies the checksum in-script before any mutation, atomically renames, refuses symlink destinations, takes a timestamped backup of existing destinations by default (`--no-backup` opts out), supports explicit `--sudo`, idempotent checksum no-op, full dry-run plans including the effective host-key checking mode, fleet `all`/`--tags` via the R48 selector with `--yes` required and bounded `-p`/`-m` parallelism; `file pull` streams through a single-invocation fetch script (checksum on stderr, bytes on stdout), refuses symlink/non-regular remote sources, writes atomic locals, and fleet pulls emit flat `<discourse>--<remote-basename>` files with pre-validated destinations. Verified end-to-end against the fake-ssh fixture. **Real-driver verification completed 2026-09-04** against three internal non-critical hosts (bawmedical, discourse.koloki.co, koloki-demo): the fixed fallback updater (SHA-256 `bc029073...`, which adds `--all --force --filter until=` to the image prunes) was pushed via `dsc file push` with `--owner root --group root --mode 0755 --sudo`, all three post-push audits report matching checksums, and each host's `update.sh --check` passes (disk healthy, no reboot pending). The pilot also caught and fixed a real bug: the default timestamped backup was silently skipped on every push (`remote_file_checksum` reports a present destination as `present`, but the existing-destination check only accepted `different`/`same` from an earlier iteration); verified live on the pilot host and pinned with a regression test (`0a7afec`). Driver: the canonical fallback update script needed controlled deployment to 16 managed hosts twice. Deliberately excludes arbitrary remote execution and recursive sync. Spec: [file-transfer](commands/file-transfer.md).
- [~] **R58 - `dsc board list|show|pull|push`** - drive the official Discourse Boards feature (core plugin, September 2026, Business/Enterprise) through its `/boards/api/*` plugin API. **Phase 1 implemented on `main`:** `board list`/`board show`/`board pull` with text/JSON/YAML output, request-budget test coverage against a mocked Discourse, and a Boards-specific hint on 404 (unlicensed/disabled/unavailable/missing board) rather than a pre-flight settings check. `pull` snapshots the entire board visible to the API user - including floater cards, not just topic cards (decided 2026-09-03, a snapshot omitting floaters would misrepresent the board) - to stable YAML/JSON with a schema version and `pulled_at`/`discourse_version` provenance, so Marcus's local-first Markdown Kanban tooling can view a Discourse roadmap as ordinary files with Discourse as write-master. Raw API models are separated from schema v1 so opaque positions, runtime fields, unknown fields, and embedded topic metadata cannot silently become future push input; floater tags use the API's `{id,name,slug}` object shape and snapshot as stable names. The board detail GET is not side-effect-free: current Discourse core runs topic-card backfill (which can create/delete cards) and writes board-view history, so `show` and `pull` disclose this behavior and refuse under global `--dry-run`. Remaining: Phase 2 guarded writes - declarative board/column/floater-card push with complete dry-run plans, topic cards by explicit `topic_id` only, and guarded `--prune` (board deletion cascades everything). Discovery complete 2026-09-03 against bawmedical (Discourse 2026.9.0), then controller/serializer behavior re-verified 2026-09-07 against core commit `a6ade3e9915f427d115f082a2ddbc6c208c5f3c1`: full endpoint/serializer shapes captured in the spec, including quirks (GET-triggered topic-card sync and view history, relative `after_card_id` ordering, whole-object column updates, bare-hex colors, `to_column_id` vs `column_id`, `direction` for column moves, silent tag-binding ignore on partial payloads, upstream `constraint-preview` 500). Driver: the Boards API is undocumented in the official API docs; without capture the shape would have to be re-derived. Deliberately excludes explicit topic mutation and constraint-fix automation. Spec: [boards](commands/boards.md).
- [ ] **R59 - `dsc upcoming-change` and `dsc setting upload`** - expose Discourse's supported Upcoming Changes API through list/show and explicit idempotent enable/disable commands, then add a validated upload-and-bind workflow for upload-type site settings. Every mutation must honor global dry-run, preserve prior state in output, and post-verify. Phase 1 deliberately excludes fleet mutation: Upcoming Changes need canaries, while curated uploads are forum-specific. Driver: Discourse's September 2026 generated `/llms.txt` is a hidden Upcoming Change, and safely replacing a third-party generator requires binding reviewed files without raw API or Rails-console workarounds. Spec: [upcoming changes and setting upload](commands/upcoming-changes-and-setting-upload.md).
- [ ] **R12 - Deterministic Chat archival and SAR inclusion** - add a read-only, bounded export of a subject's Discourse Chat data, preserving stable message metadata, threads, edits, upload references, and explicit completeness warnings in machine-readable and reviewable local files; then make it an opt-in section of `dsc sar`. The first phase is API discovery because the export must establish what the admin API can retrieve for public channels, private channels, DMs, deleted messages, and retention-expired content before promising completeness. Generic conversational `chat send` and an agent-oriented single-forum chat interface are out of scope: Discourse's built-in MCP server already reads and writes Chat for that use case. Driver: Chat messages can be personal data required for a Subject Access Request, while an MCP conversation is not a deterministic compliance archive. Spec: [chat archival](commands/chat-archival.md).

### Admin depth (demand-driven)

- [x] **R60 - `dsc emoji delete`** - implemented on `main`: `dsc emoji delete <discourse> <name>...` (alias `rm`) via `DELETE /admin/config/emoji/:name.json`, falling back to the legacy `/admin/customize/emojis/:name.json` route on 404 (the route moved in discourse/discourse#30511, January 2025). Names are matched case-insensitively against a name-existence preflight (`dsc emoji list`), so any requested name not found on the forum refuses the whole batch with a clear error instead of deleting a partial set; repeated requested names are deduplicated. A post-delete list verifies that every accepted name disappeared, catching plugin-provided emoji that appear in the admin list but are not database-backed and therefore cannot be removed by this endpoint. `--dry-run` states that references to a deleted shadowing custom emoji may fall back to a same-named built-in emoji after Discourse refreshes or rebakes them without claiming every persisted rendering changes immediately. Driver: a black custom `heart` uploaded years ago shadowed the built-in heart and, once Discourse Reactions landed in core, became the visible Like button on five managed forums; removal required hand-rolled curl against the admin API (2026-09-15, Discourse 2026.9.0). Related: R39 (emoji groups and bulk transfer) and R61 (delete-surface completeness review).
- [ ] **R61 - Delete-surface completeness review** - audit every `dsc` command family for a missing delete/destroy verb, define a systematic way to check new surfaces for the same gap before merge, and add the missing verbs. R60 closed the first known gap by adding `emoji delete`. Remaining surfaces to survey against the admin API: webhook management, user fields, badges, groups beyond the basic destroy, theme assets, categories beyond topic moves, API keys beyond revoke. Deliverables: a checklist item in the contribution/PR template ("does this command surface support every lifecycle verb the API exposes - create/read/update/delete/list?") plus roadmap entries for each confirmed gap. Driver: R60's emoji-delete discovery suggested the omission was invisible precisely because there was no review step that asked the question.
- [ ] **R39 - Emoji groups and bulk transfer** - investigate the admin API for custom emoji group assignment and ZIP/CSV bulk import/export; if available, add `dsc emoji` pull/push with manifest validation and dry-run support. - [x] **R16 - `dsc report <name> [--since]`** - implemented on `main`: a single raw Discourse admin report by id (`signups`, `topics`, `posts`, `likes`, and any other id Discourse accepts on the forum), fetched via the same `/admin/reports/{id}.json` client `dsc analytics` already wraps, with no cross-report derivation - a thin pass-through/formatter, distinct from `analytics`'s curated health dashboard. `--since`/`-s` (default `30d`) matches `analytics`'s window flag for consistency; `--format text|json|yaml`. Text output handles both Discourse report shapes (flat day-buckets and stacked multi-series charts). Report ids are not independently field-verified against a live forum in this repo - same caveat `analytics` already documents for its report ids. Spec: [analytics](commands/analytics.md#data-sources) (shared data-source section); docs: [report](../docs/report.md).

## Out of scope / removed

- ~~Shell completion *regeneration* as a tracked item~~ - superseded by the shipped `completions install`.
- ~~`dsc user password change`~~ - Discourse has no admin "set this password" endpoint by design; `user password-reset` covers the need.

Reopen only for a concrete `dsc` requirement such as deterministic export, incident evidence, or cross-forum triage; generic single-forum agent access is not sufficient.
