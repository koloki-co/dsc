# Roadmap

The single list of planned and in-progress work for `dsc`. Checked entries may be implemented on `main` but not yet released; released history lives in [CHANGELOG.md](../CHANGELOG.md). Unreleased completed work is described as "implemented on `main`", not "shipped".

Legend: [x] done, [~] in progress or partially done, [ ] not started. Stable roadmap codes (`R1`, `R2`, …) are never renumbered or reused.

## Shipped (highlights)

The built surface, grouped - see CHANGELOG for the full per-release detail.

- **Declarative sync** - `setting pull/push/diff`, `tag pull/push`/`rename`, `category pull/push` (front-matter routing, `--dry-run`, `--updates-only`, `--no-bump`/`--skip-revision`), plus `post`/`backup`/`emoji`/`topic` pull/push. Specs: [setting-sync](commands/setting-sync.md), [tag-sync](commands/tag-sync.md), [category-workflow](commands/category-workflow.md).
- **Theme management (complete)** - settings (incl. `pull/push`), fields (SCSS/HTML), assets (`set/unset`), enable/disable, attach/detach, palettes, `show`, remote `update`, API `install`/`delete`. Spec: [theme-management](commands/theme-management.md).
- **Compliance / cross-forum** - `sar` (GDPR SAR export), `setting audit` (one setting across the fleet). Spec: [subject-access-request](commands/subject-access-request.md).
- **Content** - `topic pull --full`, `topic title`/`tags`, `topic delete`/`restore`/`list --deleted`, negative-ID user-list fix. Specs: [topic-pull-full-thread](commands/topic-pull-full-thread.md), [topic-title-and-tags](commands/topic-title-and-tags.md), [topic-delete](commands/topic-delete.md), [user-list-negative-ids](commands/user-list-negative-ids.md).
- **Ops / diagnostics** - `update` (skip-if-current, rootless Docker, parallel), `harden` (PQ-hybrid SSH), `backup setup-s3` and `backup health` Phase 1, saved Data Explorer query inspection/execution. Specs: [backup-s3-setup](commands/backup-s3-setup.md), [backup-health](commands/backup-health.md), [explorer](commands/explorer.md).
- **CLI / distribution** - universal `--format`, `completions install` (+ PowerShell), `man` pages, `version --format`, SIGPIPE-safe piping, config-path resolution, cargo-dist release + git-cliff changelog, `s/version++` one-command release, push/PR CI gate. Specs: [config-path-resolution](commands/config-path-resolution.md), [cli-design](cli-design.md).


## 1.0 launch checklist

Work toward `v1.0.0`. The stable `RXX` identifiers below are intentionally non-contiguous: completed items may be retained as checked entries or summarised above, but are never renumbered or reused.

**Decision, 2026-08-26: the Meta announcement is decoupled from `v1.0.0`.** `dsc` is announced as a pre-1.0, explicitly alpha tool. This is honest about where it is, sets expectations about breaking changes, and does not require the contract items below to land first. [compatibility](../docs/compatibility.md) already scopes the CLI contract to "takes effect with `v1.0.0`; pre-1.0 releases remain subject to change", so no documentation change is needed to announce at `0.x`.

- [ ] **R54 - Agent-facing mutation controls** - adopt the useful safety patterns confirmed in CDCK's official `@discourse/mcp` 0.3.1 without duplicating its HTTP tool surface: a shared adaptive per-forum write governor that pauses all work for a host after a 429 and lowers concurrency; explicit command-family allowlists for a future `dsc job` rather than arbitrary shell or API execution; fresh-state preconditions and exact post-write verification for high-impact mutations where feasible; bounded, redacted diagnostics that distinguish an unavailable plugin/capability from a missing resource. Driver: agents and fleet jobs can amplify request bursts and mutation mistakes; the official MCP's opt-in writes, approximately one-write-per-second pacing, bounded output, and capability-specific errors demonstrate practical safeguards. ### Performance

- [~] **R52 - Performance audit remediation** - the 2026-08-10 static audit found 31 issues (5 high, 16 medium, 10 low); full findings and evidence in [performance-audit](performance-audit.md), which moved from the repository root into `spec/` on 2026-08-26 so the roadmap remains the single index. Completed and released in v0.15.0: P1-P5, P7, P17, P18, P19, P21, P31 - analytics request planning, tag pull/push idempotency, the update worker pool, SSH liveness defaults, observable readiness polling, one update-log scan, and DELETE 429 retries. Implemented on `main` but not yet released (v0.16.0): P8 - the streaming SSH runner now uses bounded `VecDeque` rings (20 lines per stream), a bounded `sync_channel(64)` for backpressure, and skips progress reconstruction when the bar is hidden; the generic `run_ssh_command` helpers that use `Command::output()` are unchanged for now, leaving `app.rs` rebuild as a follow-up. P12/P28 - a shared `run_fleet` executor in `common.rs` now backs `setting audit`, `app env audit`, and `search all`, with a centralised `fleet_worker_count` ceiling of 32; the duplicated `matches_tag_filter` implementations are retired. P30 - `fetch_fullnames` runs title discovery through a bounded worker pool for `import` and `list tidy`. P9 - SAR post-body fetches now run through a bounded worker pool (6 workers) and `posts.json` is streamed to disk element-by-element via `serde_json::to_writer` rather than building a `Vec<Value>` and calling `to_string_pretty`; `post_actions`, the raw-body map, `likes`, and `likes_json` are explicitly dropped after their sections are written. P10/P15 - the deleted-topic query filter now runs before the detail fetch, and `category_push` builds a `HashSet<u64>` topic-ID index to eliminate O(N*M) linear scans. P11 - emoji downloads now run through a bounded pool (4 workers) with an 8 MiB image-size cap. P6 was investigated and deliberately closed as "not fixing" (caching the latest SHA would make later forums in a multi-hour fleet update compare against a stale reference). P11's inline-emoji timeout was fixed under R50, leaving only its bounded-download-pool half. `tests/request-budget-test.rs` now covers request-budget regression across several of the classes already fixed. P25 - `category def push` planning now matches file entries against a `ServerIndex` (`HashMap` by id/slug/name) built once per push instead of re-scanning the server category list per entry, eliminating the `O(file categories * server categories)` linear matching; list-comparison cloning/sorting in `changed_fields` is unchanged. Outstanding, in the audit's own recommended order: P27 (SSH multiplexing decision), P28's `backup create` per-forum dry-run plan, P9's remaining serial PM-topic fetches and combined pagination walk, P10's remaining bounded topic-detail concurrency and double local-file parse, P11's P16 half (multipart upload streaming and endpoint caching), P13/P14 (paged S3 folding), and P20/P22/P23/P26 (lower-priority streaming, durability, and budget work).

### Content sync

- [~] **R49 - `dsc topic change-owner`** - Phase 1 implemented on `main` and verified against live ACCM on 2026-08-25: `dsc topic change-owner <discourse> <topic_id> <username> [--post <post_id>]...` reassigns the visible author of a topic's OP (or, with repeatable `--post`, specific replies) via `POST /t/{id}/change-owner.json`, validating the target username against the Discourse, sending the canonical-cased username required by that endpoint, and honouring `--dry-run`. Phase 2 implemented on `main`: `dsc post change-owner <discourse> <post_id> <username>` resolves the post's topic (the same lookup `dsc post info` uses) and delegates to `topic change-owner` scoped to that one post, for when the operator has a post ID but not its topic ID. Remaining: Phase 3's bulk file-driven mode. Driver: content compiled from a staff member's source document, posted via `dsc topic new` under the operator's own admin account, then needing reassignment to the actual author (ACCM Discourse, `kitchen.culinarymedicine.org`). Spec: [topic-post-ownership](commands/topic-post-ownership.md).
- [ ] **R51 - Ownership reassignment beyond topics and posts** - R49 gave `dsc` a `change-owner` verb, but only for topic and post authorship. Several other Discourse entities carry an owner or creator that an administrator may legitimately need to reassign, and `dsc` currently exposes none of them. Confirmed gaps as of 2026-08-26: `dsc group` has `list`/`info`/`members`/`add`/`copy` but **no owner surface at all**, even though group owners are a first-class Discourse concept distinct from membership; `dsc invite` has `send`/`bulk` with no notion of the invite's `invited_by` creator. Others worth surveying before designing: saved Data Explorer queries (`created_by`), uploads (`user_id`), personal-message participants, badges, and reviewable claims. Phase 1 is **discovery, not implementation**: for each entity, establish whether the admin API exposes reassignment at all, capture the exact request and a redacted response against a live Discourse, and record which are genuinely reassignable versus immutable audit fields. Only then design the surface - the open question is whether these become `dsc group owner add/remove`-style entity-native verbs or a consistent `change-owner` verb repeated per noun, and consistency with `dsc topic change-owner` should not be assumed to be the right answer for a group, where "owner" is a set rather than a single author. Driver: the same real need that produced R49, generalised - an administrator reorganising a forum needs to hand over entities created under the wrong account. Related: [topic-post-ownership](commands/topic-post-ownership.md).
- [~] **R44 - `dsc post info`** - Phase 1 shipped: read-only lookup from a post ID to minimal metadata and a canonical topic URL, including staff-visible soft-deleted posts and topics, returning post ID, topic ID, post number, URL, deletion state, and topic title/slug/category ID without emitting raw post content or author data. Driver: completed Reviewables and staff action logs identify spam posts but do not expose a URL suitable for Discourse AI spam-detector testing. Remaining: Phase 2 read-only `dsc reviewable list` surface, deferred pending a captured admin API response. Spec: [post-info](commands/post-info.md).
- [~] **R29 - `dsc render` template placeholder substitution** - Phase 1 implemented on `main`: `dsc render <discourse> <file> [-o <output>] [--format text|json|yaml]` substitutes `{{ variable }}` placeholders using the Tera engine, resolving `forum_baseurl`/`forum_name`/`forum_fullname` built-ins, `[template.vars]` globals, and per-forum `[discourse.template]` overrides; unknown variables warn to stderr and render as empty, and `--dry-run` previews the resolved variable map. Phase 2 implemented on `main`: `--strict` turns unknown variables into a single hard error naming every one of them, `--list-vars` prints a forum's fully resolved variable map (text/JSON/YAML) without reading a template file, and the `--render` flag on `topic new`/`topic push`/`topic reply`/`category push` applies the same (always non-strict) substitution inline before the file(s) are sent, composing with `--dry-run`. Remaining: code-fence protection (Phase 2). Driver: 24-template content-templates library in the discourses workspace. Spec: [template-rendering](commands/template-rendering.md).
- [~] **R11 - `category` definition sync Phase 2/3** - Phase 1 is released. Released in v0.15.0: `category rename`, explicit live `category diff`, list-field `--append`/`--remove`, `required_tag_groups`, category type IDs, complete scalar custom-field maps, parent-by-name resolution, up-front parent validation, and `topic_title_placeholder` round-trip. Remaining: logo/background assets, `icon`/`emoji`, same-file parent/child creation with cycle detection, and guarded `def push --prune`. Driver: York Music Marketplace needs the Discourse `support` category type to enable accepted answers, not an ignored `solved_enabled` category field. Spec: [category-definition-sync](commands/category-definition-sync.md).

### New command surfaces

- [~] **R53 - `dsc file audit|push|pull`** - checksum-driven regular-file transfer over the SSH hosts already configured in `dsc.toml`, with the fleet scope first and explicit (`dsc file push all <local-path> <remote-path>`), complete dry-run plans, idempotent checksum comparison, same-filesystem staging and atomic replacement, symlink refusal, timestamped backup on replacement, explicit non-interactive sudo, bounded fleet execution, and structured partial-failure results. Fleet pulls write flat `<discourse>--<remote-basename>` files such as `output/rcgp--update.sh`, avoiding ambiguous nested output trees and filename collisions. Phase 0 complete: SSH process construction centralised in `commands::ssh`; bounded binary `run_ssh_capture`/`run_ssh_pipe` added; `app.rs` and `theme.rs` migrated to shared transport; host identity policy decided (inherits the existing `accept-new`/`DSC_SSH_STRICT_HOST_KEY_CHECKING` mechanism); the no-follow stage-and-replace protocol is implemented as `commands::ssh::build_replace_script` and verified end-to-end (missing/existing destination, symlink refusal, backup, mode) against a new isolated SSH fixture (`tests/fixtures/fake-ssh`, resolved via `PATH` in place of the real `ssh` binary, that really executes the received remote command against a local scratch directory rather than pattern-matching canned responses). Phase 1 implemented on `main`: single-forum `dsc file audit` and `dsc file push` built on the shared transport and protocol, with a complete dry-run plan (now including the effective host-key checking mode), checksum verification before rename staged in-script and re-checked client-side, and `--yes` confirmation. Backup default decided 2026-08-29: a timestamped backup of an existing destination is taken automatically; `--no-backup` opts out. Remaining: Phase 2 (fleet `all`/`--tags` push and audit via the R48 selector and `run_fleet`, `--yes` + full dry-run target enumeration) and Phase 3 (pull). Driver: the canonical fallback update script has now needed controlled deployment to 16 managed hosts twice; today's workaround composes `dsc list`, `jq`, `scp`, `ssh`, `sudo install`, backups, validation, and checksum reconciliation by hand. Deliberately excludes arbitrary remote command execution and recursive sync so this remains a narrow operational primitive rather than an Ansible replacement. Spec: [file-transfer](commands/file-transfer.md).

### Cross-forum (the multi-install headline)

- [ ] **R20 - `dsc report all <name>`** - aggregate a report across forums.
- [~] **R48 - Fleet selector and output normalization** - selector unification implemented on `main`: `backup create`, `backup setup-s3`, `backup health`, `search all`, and `user find` now share one `selected_discourses` helper (`src/commands/common.rs`) that rejects an explicitly empty `--tags` filter (e.g. `--tags ""`) instead of silently matching the whole fleet. `backup create` and `search all` gained `--tags`; `user find` gained `--tags` to narrow its always-fan-out default. `search`'s two-positional grammar (`discourse`, `query`) cannot take a true `--all` flag without breaking positional order (a clap constraint: an optional positional cannot precede a required one) or reordering the arguments, which would itself be a breaking change - so `search all <query>` remains the compatibility-preserving trigger and `--tags` layers onto it. ## Out of scope / removed

- ~~Shell completion *regeneration* as a tracked item~~ - superseded by the shipped `completions install`.
- ~~`dsc user password change`~~ - Discourse has no admin "set this password" endpoint by design; `user password-reset` covers the need.
- ~~`dsc user anonymize`~~ - rare enough for the Admin UI; not worth the destructive-confirmation UX.
- ~~`api-key create --scope`~~ - **parked 2026-06-29**. Scoped keys are low-value for `dsc` (nearly everything needs admin scope anyway) and blocked on an unconfirmed scoped-key `POST /admin/api/keys.json` body. Full-admin `api-key create` stays. Revisit on a concrete least-privilege consumer.
